# Juvi Android — Google Play release (design)

**Date:** 2026-10-12
**Status:** design — awaiting user review before the implementation plan is written
**Related:** `mobile/README.md` (Release signing, Firebase), `docs/juvi/account-deletion-retention.md`,
`docs/superpowers/plans/2026-10-03-juvi-notifications-3-mobile.md` §"Real-device verification" step 3,
`.sdd/specs/011-account-deletion/`

## 1. Goal

Get the Juvi Android app (`in.juvion.juvi`) onto Google Play on the **Internal testing** track, with a
correctly **release-signed App Bundle**, and with the store-listing and policy deliverables Play
requires. Establish the signing setup so that a later phase can automate releases from CI.

Success = a signed `app-release.aab` uploads to Internal testing without Play rejecting it for
signing, a privacy-policy URL and an account-deletion URL are live, and the store listing (title,
descriptions, icon, feature graphic, screenshots) is complete.

## 2. Scope

In scope:
- A fresh release **upload keystore** with a known password, plus the local `key.properties` that
  `android/app/build.gradle.kts` already reads.
- Hardening `mobile/android/.gitignore` so no keystore can be committed.
- A hosted **privacy policy** page (the deletion section already drafted becomes part of it).
- A **store listing copy** draft and an asset requirements checklist.
- A **Play Console walkthrough** (operator steps) and a release checklist doc.

Out of scope (later work):
- CI-driven Play publishing (Phase 2 — see §5.5).
- iOS / App Store.
- Any change to app behaviour, the backend, or the API contract.

## 4. Key decisions

1. **Generate a fresh upload keystore; abandon `mobile/android/juvion`.**
   *Why:* the old keystore's password is unrecoverable, and nothing is bound to it — no app exists in
   Play yet, and the app uses no Firebase feature that keys on the signing-cert SHA-1. A new upload
   key costs nothing and Play App Signing will hold the long-lived app-signing key anyway.
   *How to apply:* keep the legacy file on disk but git-ignore it; do not delete it in this work
   (delete only on explicit request).

2. **Play App Signing, upload key = the new keystore.** Google holds the app-signing key; we keep the
   upload key. This is Play's default for new apps and makes a lost upload key recoverable.

3. **First release to Internal testing, not Production.** Fast (no full review), and it exercises the
   real push/notification path on real devices before a public release.

4. **Password generated by the assistant this session.** A strong random value, shown once; the user
   stores it in a password manager and in the GitHub secret. Nothing is registered against it yet, so
   rotation later is free.

5. **Privacy policy is a static page in the portal's `public/` dir**, served at
   `https://juvion.in/privacy-policy` — the same hosting path as the deletion page, so no
   new host or nginx rule is needed.

## 5. Design

### 5.1 Signing

- Generate `mobile/android/app/upload-keystore.jks`, alias `upload`, RSA 2048, validity 10000 days,
  store password = key password = a generated strong password. (Storetype left at keytool's default,
  PKCS12; AGP auto-detects it on read. If a read ever fails, add `storeType` to the signing config.)
- Create `mobile/android/key.properties` (git-ignored, already covered by `.gitignore`):
  ```
  storeFile=upload-keystore.jks
  storePassword=<generated>
  keyAlias=upload
  keyPassword=<generated>
  ```
  `storeFile` is relative and resolves from `android/app/` (`build.gradle.kts:47`).
- Harden `mobile/android/.gitignore`: add the legacy `/juvion` path and `**/*.p12` alongside the
  existing `key.properties`, `**/*.keystore`, `**/*.jks`.
- Verify: `flutter build appbundle --release` then `keytool -printcert -jarfile
  build/app/outputs/bundle/release/app-release.aab` shows the `CN=…, alias upload` cert, not the
  Android debug cert.
- Version rule: `versionCode` in `pubspec.yaml` must increase for every upload. First upload keeps `1`.

### 5.2 Privacy policy page and hosting

- Add `admin-portal/public/privacy-policy.html`: a static, script-free page in the visual style of
  `account-deletion.html` (its header comment explains the no-script / plain-form constraints, which
  this page inherits). Content covers: what data is collected (account + session data, per-device push
  registration, notification deliveries and their status, server-side usage events, profile photo),
  why, retention, third parties (Firebase Cloud Messaging, Google Play / Crashlytics), how to request
  deletion (linking `/account-deletion.html`), and a contact address.
- The deletion section is taken verbatim in substance from `docs/juvi/account-deletion-retention.md`.
- After the portal's next deploy (`scripts/deploy.sh`), the two Play URLs are live:
  - Privacy policy: `https://juvion.in/privacy-policy`
  - Account deletion: `https://juvion.in/account-deletion`

### 5.3 Store listing content (deliverable)

- Draft copy for: app **title** (≤30 chars), **short description** (≤80), **full description**
  (≤4000), and the **release notes** for the internal-testing release.
- Asset checklist the user must supply (Play's current specs): app icon 512×512 PNG (32-bit, ≤1 MB);
  feature graphic 1024×500 PNG/JPEG; ≥2 phone screenshots (min 320 px, ≤3840 px, 16:9 or 9:16).
- All copy and the checklist live in `docs/juvi/play-store-release.md` (new).

### 5.4 Play Console configuration (operator steps — documented, not code)

1. Create the app: name "Juvi", default language, app (not game), free.
2. Enable **Play App Signing**; upload the AAB signed with our upload key.
3. **App content**: Privacy policy URL; Data safety form (answer from
   `account-deletion-retention.md` §"Operator notes"); content rating questionnaire; target audience;
   ads = No; government app = No; financial features per the app's actual scope.
4. **Internal testing** track (or a dedicated "Internal testing" release), upload
   `app-release.aab`, add tester emails, roll out.
5. Confirm the account's developer display name matches the "Juvion" name used in
   `account-deletion.html` (its `:37-38` asks for this).

### 5.5 Phase 2 — CI automation (a later plan, sketched here only)

Add a Play publish job to `.github/workflows/mobile.yml`, gated the same way the signed-AAB step
already is (`IS_MAIN_PUSH` + real Firebase), using a Play **service account** JSON stored as the
secret `PLAY_SERVICE_ACCOUNT_JSON`. Two candidate mechanisms — pick one during the Phase 2 plan:
`r0adkll/upload-google-play` (YAML only) vs fastlane `supply` (store listing as code). The existing
release step already produces `mobile/build/app/outputs/bundle/release/app-release.aab`
(`mobile.yml:66-71`), so the addition is a single publish step after it.

## 7. Verification

- `flutter build appbundle --release` succeeds and the AAB is signed by the `upload` alias
  (`keytool -printcert -jarfile`), not the debug key.
- `git status` shows no keystore as untracked-and-committable; `git check-ignore` reports the new
  keystore, `key.properties`, and the legacy `juvion` as ignored.
- The privacy-policy page renders with no console errors and its deletion link resolves.
- Play Console accepts the AAB on the Internal testing track (no signing rejection).

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Upload keystore committed to git | `.gitignore` hardening + `git check-ignore` verification before any commit |
| Keystore password lost again | Password handed to the user once for a password manager + GitHub secret; Play App Signing makes a future loss recoverable |
| Store listing rejected for missing/incorrect policy | Data-safety answers derive from `account-deletion-retention.md`; the policy page states the same retention facts |
| versionCode not incremented on a later upload | Documented as a release rule in `play-store-release.md` |

## 9. Inputs required from the user

- Store-listing assets: icon 512×512, feature graphic 1024×500, ≥2 phone screenshots.
- A contact email and a developer/entity name for the policy page and the Play account.
- GitHub secrets (Phase 2): `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
  `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, and later `PLAY_SERVICE_ACCOUNT_JSON`.

## 10. Sequence

1. Signing: generate keystore, write `key.properties`, harden `.gitignore`, verify a signed AAB.
2. Privacy policy page; deploy the portal; confirm the URL.
3. Store listing copy + asset checklist in `docs/juvi/play-store-release.md`.
4. Play Console walkthrough → upload the AAB to Internal testing.
5. (later) CI automation — its own plan.
