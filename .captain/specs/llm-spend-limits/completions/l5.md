## Spec Gaps Discovered

1. **Plan §1.9 logs `pct=NaN%` for zero-limit colleges.** The plan's example log line divides `totalCost / weeklyInr * 100`. When `weeklyInr === 0` (the bypass case — most new colleges), this is `NaN`. The worker emits `pct=0` instead, which is the correct admin-facing reading ("we didn't have a limit, we have used 0% of nothing"). Plan should be updated to clarify the divide-by-zero guard. Documented inline at the log site in `llm-usage-weekly.worker.ts`.
2. **`mongoose` `timestamps:true` overrides explicit `createdAt` on `.create()`.** The L5 tests had to patch `createdAt` via `AgentAction.collection.updateOne` to position actions inside / outside the test window — an `await AgentAction.create({ ..., createdAt })` silently has its `createdAt` overwritten by Mongoose. Captured as a defensive pattern in the test file's `seedAction` helper for future cron-window tests to copy.
3. **Per-college failure surfaces only via `console.error`.** The current implementation logs and continues — there is no audit row written for failed colleges (unlike `FeeAlertsCronRun.topLevelError` from the fee-alerts-cron precedent). The plan §1.9 didn't call for a per-run audit table for the LLM cron, and tasks.md §L5 doesn't ask for one. If observability becomes a concern, a follow-up task could add a thin `LLMUsageCronRun` mirror of `FeeAlertsCronRun`. Not blocking L5.

## Notes / Design Decisions

- **Time helpers in UTC, exported.** `startOfLastWeek` / `endOfLastWeek` are pure functions taking an optional `now` arg (defaults to `new Date()`). This makes the boundary math directly testable without `vi.setSystemTime` for the helper itself, and lets future code (e.g. an admin "rerun last week's cron" button) reuse the same boundaries. Algorithm: walk back to the most recent UTC Monday, then subtract 7 days — so the COMPLETED week is what we hand back, never the in-progress week.
- **Bounded fan-out via existing `withBoundedConcurrency`.** Re-uses the helper from `modules/juvi/finance-agent/orchestrator-helpers.ts` (already battle-tested in L3 risk-narrative + reminder-draft batches). No new deps. The concurrency-counter test (test #7) instruments the AgentAction.aggregate stub to verify peak in-flight stays ≤ 10 and is > 1 (not accidentally serial).
- **`LLMUsageSnapshot` row written even for zero-weeks.** The contract's "sanity test" requires this — admins should see an explicit zero-spend row, not a missing one. Implemented as a no-op-friendly insert (no `if (totalCalls > 0)` short-circuit).
- **Per-college try/catch lives INSIDE the bounded-concurrency callback** (not as a `Promise.allSettled`-style filter). This keeps the BullMQ job's exit code SUCCESS even when N colleges fail — so the job doesn't trigger a job-level retry that would re-run the WHOLE cohort. Per-college issues are logged with `[llm-budget:weekly] college=<id> error: ...` and become an SRE / log-grep concern, not a retry storm.
- **Structured log line matches plan §1.9 verbatim.** `[llm-budget:weekly] college=<id> spent=<n> limit=<m> pct=<p>` — greppable and identical to the format that future Datadog / ELK alerts will key off.
- **`LLM_USAGE_WEEKLY` placed under the `platform:` namespace** (not `juvi:`). Rationale: the cron is a platform-level governance worker — it doesn't read or write Juvi conversation state, only `AgentAction` metadata. Mirrors the placement of `NOTIFICATION` / `EMAIL` / `SMS` under `platform:`.
