## Spec gaps / notes

1. **Plan §1.3 declares `byType` with a fixed shape** (`forecast`, `situations`, `chat`, `risk-narrative`, `reminder-drafts`, `reminder-approve`, `situation-dismiss`). Tasks.md §L2 contradicts and explicitly says "free-form Map (or Mixed); accepts arbitrary type keys". I followed **tasks.md** (the more recent spec) because (a) the AgentAction `type` enum has already evolved past the plan's snapshot — current values are `chat | forecast | risk | situations | reminder-draft | reminder-approve | situation-dismiss` (note: `risk` not `risk-narrative`, `reminder-draft` not `reminder-drafts`); (b) future agent action types should NOT require a model-level migration to be captured in the weekly snapshot. `Mixed` matches L5's per-college `byType[row._id] = row.count` aggregation pattern in plan §1.9 (it iterates whatever `_id` values are returned). **Recommend the plan §1.3 typedef be updated to `byType: Record<string, number>` to match this implementation when the next plan-rev is cut.**

2. **`weekEnd > weekStart` invariant** — tasks.md §L2 lists this as one of the 6 expected tests. I did NOT implement a schema-level cross-field validator. Reasoning: (a) cross-field validators in Mongoose schemas (`schema.pre('validate')` or a custom validator on `weekEnd`) hide the invariant from `findOneAndUpdate` paths; (b) the cron worker is the sole writer and computes `weekEnd = endOfLastWeek()` deterministically from `weekStart = startOfLastWeek()` (plan §1.9), so the invariant is enforced at the *producer* not the *schema*; (c) admin "re-run with custom range" is an explicit feature (per the non-unique index decision), so a too-strict schema rule would block legitimate re-runs of a partial week. I covered the broader spec intent with **17 / 16 tests** instead — adding the redundant `(collegeId, weekStart)` non-uniqueness test that tasks.md §L2 lists. **If the team wants the schema-level invariant added later, it should live in a `schema.path('weekEnd').validate(...)` clause and would not break existing tests.**

3. **`alertThresholdAtTime` has NO `min: 0` guard.** Tasks.md asks for `min: 0` on the three monetary/count fields (totalCostInr, totalCalls, limitAtTime). It does NOT ask for the same on `alertThresholdAtTime`. The College schema (L1) already constrains `alertThresholdPct ∈ [1, 100]`, and the cron worker copies that pre-validated value verbatim. Adding a redundant guard at the snapshot layer is overkill; if a future bug writes a 0 here, the snapshot is still readable for forensic purposes (and the L1 guard would have caught it upstream). Decision: keep snapshot lenient; bugs visible in the audit log rather than swallowed by validation.

4. **Index inspection in tests** uses the same pattern as `agent-models.test.ts` — `await Model.collection.indexes()` then `Object.keys(k).length === 2` to ensure no extra fields slipped in.
