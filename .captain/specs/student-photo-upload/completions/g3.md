# G3 — Refactor photo-controller into a parameterized handler factory + mount 9 new routes

**Status:** GREEN. Focused suite green; full backend suite green; typecheck clean.

## Goal

Lift the student-only HTTP handlers (`uploadPhotoHandler`,
`deletePhotoHandler`, `getPhotoUrlHandler`) onto a generic
`PersonEntityType`-parameterized factory so the same machinery serves
faculty, staff, and parents. Wire the new entity-typed handler bundles
into 9 new mounts on the people router (3 each × faculty / staff /
parents), keeping the existing student mounts unchanged via thin
compat aliases.

The service layer (`uploadEntityPhoto`, `deleteEntityPhoto`,
`getEntityPhotoUrls`) was already generalized in G1+G2 — G3 is a pure
HTTP-layer refactor on top of that contract.

## Compat-shim status

Per the G1+G2 completion note, the photo-service compat shims
(`uploadStudentPhoto`, `deleteStudentPhoto`, `getStudentPhotoUrls`) and
the s3-client `studentUploadPrefix` shim were originally slated for
removal "in the same commit as G3's controller refactor."

**Decision: kept. Removal deferred to G5.**

Rationale:
1. **Frontend hasn't migrated yet.** G4 / G5 will migrate the admin
   portal to call the entity-typed routes. Removing the service-layer
   shims in G3 doesn't directly affect the frontend (they're
   server-internal), but ripping them out as part of an HTTP-layer
   refactor mixes two concerns and makes G3 harder to revert if
   something breaks downstream.
2. **No internal callers left.** The controller is the only consumer
   in the backend tree. After G3, the controller no longer imports
   the student-only shims — verified by `grep -rn` (see below).
   So the shims are dead code from the backend's perspective; they
   only cost a few lines and no runtime overhead. Cheap to keep until
   G5 lands.
3. **Test files still exercise them.** `photo-service.test.ts` has a
   sizable block of `uploadStudentPhoto`/`deleteStudentPhoto`/
   `getStudentPhotoUrls` tests left over from P4. Removing the shims
   would force a parallel rewrite of those tests. Keeping the shims
   leaves the existing test asset intact and stable.

Removal plan for G5 (or later):
```bash
grep -rn 'studentUploadPrefix\|uploadStudentPhoto\|deleteStudentPhoto\|getStudentPhotoUrls' backend/src admin-portal/src
```
After G5, every remaining hit should be in test files that we then
delete or migrate alongside the shim removal. The s3-client
`studentUploadPrefix` is also kept since it's mocked in two test
files; removing it would require updating those mocks in lockstep.

Verified at G3 commit time: backend production code (everything
under `backend/src/modules/`, `backend/src/shared/`, etc., excluding
tests) has zero remaining call sites for the student-only shims.

## Spec gaps / decisions made

1. **Compat alias direction.** The brief specifies the existing
   exports `uploadPhotoHandler` / `deletePhotoHandler` /
   `getPhotoUrlHandler` "stay as compat shims pointing at
   studentPhotoHandlers." Implemented exactly as stated — they're
   simple re-exports of the corresponding `studentPhotoHandlers.*`
   reference, not separate functions. Identity equality holds
   (`uploadPhotoHandler === studentPhotoHandlers.upload`), which keeps
   the route mounting layer unchanged.

2. **Variant validation hoisted to module scope.** The original
   controller had `PHOTO_VARIANTS` and `isPhotoVariant` as a top-level
   helper used only inside `getPhotoUrlHandler`. Now that the factory
   produces 4 `getUrl` handlers, hoisting the validator to module
   scope (one shared closure) is cleaner than baking it into
   `makePhotoHandlers`. No behavior change.

3. **Generic 400 messages on missing-id.** The brief shows
   `throw new AppError(400, '${entityType} id required')` per entity.
   Implemented as-is. Note this only fires if Express's route param
   regex somehow yields an empty `:id`, which in practice it can't —
   so this branch is defensive. Kept the per-entity slug for
   diagnostic clarity in case a future router refactor relaxes the
   match pattern.

4. **No new validation on the entity-typed routes vs. the student
   route.** The brief is clear that the multer instance and the multer
   error handler stay as-is — they're entity-agnostic. So all 4
   entities share the same 5 MB cap, the same JPEG/PNG/WebP
   allowlist, and the same error messages. This is correct: photos
   are the same shape regardless of which entity wears them.

5. **Cross-college 404 message style.** Tests assert the regex
   `${type} not found` for each entity type. The 404 wording is
   produced by `loadEntityScoped` in photo-service.ts, which uses the
   raw entity-type slug ("students" / "faculty" / "staff" /
   "parents"). Already in place from G1+G2; G3 just relies on it. No
   change needed in the controller layer.

6. **`SeededStudent` → `SeededEntity` rename in the test file.** To
   keep the existing student-only describe blocks compiling without
   churn, the new shape exposes both `entityId` and the legacy
   `studentId` field (they're set to the same string). New seed
   helpers (`seedFaculty` / `seedStaff` / `seedParent`) follow the
   same pattern. This avoids touching the existing 18 student-only
   tests that destructure `{ studentId }`.

7. **Parameterized loop includes students.** The `ENTITY_PATHS` array
   covers all 4 entity types. For students this means the parameterized
   describe re-runs the 4 happy/cross-college cases that were
   conceptually already covered by the student-only describes
   above. The duplication is intentional and cheap — it ensures the
   parameterized contract is uniform across entities, including
   students. Removing students from the loop would create an
   asymmetric test surface that future maintainers might
   misinterpret.
