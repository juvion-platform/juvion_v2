# P2 Completion Signal — Person.photo structured field

**Task:** Replace flat `photo: String` on the `Person` model with a structured
sub-document holding original + thumbnail S3 keys plus upload metadata.

## Schema — before / after

### Before

```ts
// backend/src/models/people/Person.ts
export interface IPerson extends Document {
  // ...
  photo?: string;
  // ...
}

const schema = new Schema<IPerson>({
  // ...
  photo: String,
  // ...
});
```

### After

```ts
// backend/src/models/people/Person.ts
export const PERSON_PHOTO_CONTENT_TYPES = [
  'image/jpeg',
  'image/png',
  'image/webp',
] as const;

export type PersonPhotoContentType =
  (typeof PERSON_PHOTO_CONTENT_TYPES)[number];

export interface IPersonPhoto {
  original: string;        // S3 key of original
  thumb: string;           // S3 key of thumbnail
  contentType: PersonPhotoContentType;
  sizeBytes: number;
  uploadedAt: Date;
}

export const photoSchema = new Schema<IPersonPhoto>(
  {
    original:    { type: String, required: true },
    thumb:       { type: String, required: true },
    contentType: { type: String, enum: PERSON_PHOTO_CONTENT_TYPES, required: true },
    sizeBytes:   { type: Number, required: true, min: 0 },
    uploadedAt:  { type: Date,   required: true },
  },
  { _id: false },
);

export interface IPerson extends Document {
  // ...
  photo?: IPersonPhoto | null;
  // ...
}

const schema = new Schema<IPerson>({
  // ...
  photo: { type: photoSchema, default: undefined },
  // ...
});
```

The whole `photo` field stays optional at the document level (`default: undefined`,
no `required: true` on the parent). When a `photo` object is present, all five
nested fields are required and `contentType` is enum-restricted.

## Migration plan (follow-up — NOT in P2 scope)

The field was previously declared `photo: String` but no production code ever
wrote it (verified earlier in the spec). Mongoose will silently drop any
legacy `photo: '<string>'` value on read because the new sub-schema cannot
cast a string. If the dev-seed or any deployed environment turns out to have
legacy string values, P3/P4 can run a one-shot script:

```ts
await Person.updateMany(
  { photo: { $type: 'string' } },
  { $unset: { photo: '' } },
);
```

No migration script is added in this task per the work-order's instruction.

## Spec gaps / open questions

1. **What does `SearchResult.photo` mean to the UI?** P4 needs to know whether
   the search card wants `thumb` only, or the whole structured object. The
   current code returns the raw string — keeping the same shape (just a URL)
   is the smallest change.
2. **Validation surface for `photo` in basePersonSchema** — does the
   structured photo go through the generic Person create/update body, or
   exclusively through the upload endpoint? Cleanest answer: upload endpoint
   only. P4 should drop `photo` from `basePersonSchema` and from the five
   service.ts allowlists.
3. **Index?** The S3 keys in `photo.original` / `photo.thumb` are not queried,
   so no index is added. If P4 introduces "find person by S3 key" lookups,
   add a sparse index then.
