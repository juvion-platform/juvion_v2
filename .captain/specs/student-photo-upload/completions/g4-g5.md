# G4 + G5 — Rename + parameterize photo components and wire to all 4 person types

**Status:** GREEN. `npx tsc -b admin-portal` clean (0 errors); `npm run build -w admin-portal` succeeds.

## Goal

Lift the student-only frontend photo components onto an entity-aware
`PersonEntityType`-parameterized API so the same UI machinery can serve
faculty, staff, and parents — mirroring the backend G3 controller
factory. Then wire the renamed components onto all 4 person detail
pages and all 4 person list pages.

The frontend service helpers, the in-page detail block, and the list
thumbnail were all student-only after P1–P7. G4 generalized them by
threading a `PersonEntityType` discriminator through every call site
plus the React Query cache keys. G5 wired the renamed components onto
the three remaining detail pages (Faculty / Staff / Parent) and the
three remaining list pages (FacultyPage / StaffPage / ParentsPage),
leaving the existing Student wiring intact via prop renames.

## Decisions / spec gaps observed

1. **Parent detail page hosts two modes (view + edit) on one screen.**
   The brief describes inserting the photo block "above the first
   DetailSection block." On Parent the first DetailSection lives inside
   a `{editMode ? (...) : (...)}` ternary — placing the block inside
   either branch would hide it in the other mode. Decision: inserted
   the block between the header `</div>` and the ternary opener, so it
   stays visible in both modes. Matches the user-facing intent (the
   parent should be visually identifiable on entry regardless of
   mode), and avoids duplicating the JSX inside both branches.

2. **Parent edit mode hosts an inline form (not a separate route).**
   Because Parent records were never given a dedicated edit route
   (ParentsPage uses a modal; ParentDetailPage hosts inline edit),
   placing the photo block above the form means uploads/deletes happen
   on the Mongo `Parent._id`, which is the same id the form is
   editing. Backend G3 mounts `POST /api/people/parents/:id/photo`
   keyed off the Parent's `_id`, so this works directly.

3. **Compat-shim policy.** Per the G3 completion memo, the backend
   compat shims (`uploadStudentPhoto` etc. on the photo-service) are
   kept until G5 lands. G5 only touches the **frontend** — backend
   shims are untouched here. The frontend now exposes its own deprecation
   path: `uploadStudentPhoto / deleteStudentPhoto / getStudentPhotoUrl`
   in `services/people.ts` are now thin `@deprecated` wrappers over
   `uploadEntityPhoto('students', …)` etc. They can be removed in a
   follow-up after a final scan confirms no straggling consumers.

4. **Column positioning.** The brief says "leftmost position (or
   wherever the existing avatar/initials lives — replace the existing
   one)." None of Faculty / Staff / Parents had an existing avatar
   column, so the new `photo` column is added as the literal first
   element of the `columns` array on each list page. This matches the
   Students page (which already had it leftmost via the previous
   StudentThumbnail wiring).

5. **Generic ARIA / status copy on `PersonPhotoBlock`.** The original
   `StudentPhotoBlock` used "Student photo" and "Delete this student's
   photo?" — those strings have been swapped to entity-agnostic
   "Profile photo" / "Delete this photo?". The brief is silent on copy,
   but the alternative (threading entity-display-name strings through
   props) felt over-engineered for a v1 generalization.

6. **No new permission gates.** Per the brief's role-gating note, all 4
   entity types share the same `useAuthStore(s => s.hasPermission('people','update'))`
   gate. Mirrors the backend (which uses a single
   `authorize('people','update')` middleware on every photo route, per
   G3).

7. **No new dependencies added.** All renamed files use the same
   imports as their predecessors. No churn in `package.json`.
