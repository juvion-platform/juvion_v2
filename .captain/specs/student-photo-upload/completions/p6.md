- [x] **Has-photo state.** 96×96 `object-cover` thumb image driven by the presigned URL, "Uploaded {date}" copy (only when `lastUploadedAt` is known — see "uploadedAt source" note below), `[Replace]` + `[Delete]` buttons.

- [x] **Error state.** Two surfaces: (a) inline picker errors ("File too large", "Unsupported format") under the avatar with a "Try again" link; (b) upload-failure errors inside the confirm-upload modal in a red banner with the modal's "Confirm upload" button relabeled to "Try again".

- [x] **File picker.** Hidden `<input type="file" accept="image/jpeg,image/png,image/webp">` triggered by button clicks; size & MIME validated client-side before any network call.
- [x] **Preview modal.** `URL.createObjectURL(file)` thumbnail, `[Confirm upload]` + `[Cancel]`. Object-URL cleanup runs in two places: a `useEffect` cleanup hook AND the `closeUploadModal` helper, so leaks are impossible regardless of which flow tears the modal down.

## Spec gaps / notes

1. **`uploadedAt` source.** The presigned-URL endpoint (`GET /photo-url`) returns only `{ url, expiresAt }` per variant — it does NOT return the photo's `uploadedAt`. The metadata is only in the `POST /photo` response. As a result, "Uploaded {date}" copy is shown only after a fresh upload completes in this session; on a cold page load with an existing photo it falls back to "Photo on file". This is intentional and consistent with the wire contract; if "uploadedAt" needs to be visible on cold reload, the cleanest path is to bake it into the existing `getStudent(id)` response (which already populates the `person` subdocument that owns `photo.uploadedAt`) rather than adding a new endpoint. Flagging for downstream tasks; out of scope for P6.
2. **AbortController / cancel button.** Deliberately deferred for v1, per the brief's "optional for v1" allowance. Files ≤ 5 MB on a typical broadband connection complete in 0.2–1.5 s — short enough that a cancel button is harmful UX more often than it helps. If we add it later, the wiring is two lines: `axios.CancelToken` (or `AbortController` with `signal: controller.signal` on the axios call) inside `uploadStudentPhoto`, plus a `controller.abort()` call wired to the modal's "Cancel" button when `uploadMutation.isPending`.
3. **Toast pattern reuse.** Duplicated the `SituationToast` pattern from `FeeDashboardPage.tsx` rather than refactoring it into a shared `components/ui/Toast.tsx`. Shared extraction is a 4-file change (this component + the two existing toast users + the new shared file); held off because (a) the brief explicitly says "If no shared toast exists, inline a small fixed-position toast component" and (b) extracting would have widened P6's surface area beyond the listed scope. Logged as a candidate refactor for a future sweep — three near-identical 60-line blocks now live in three files (`FinancialHoldsPage`, `FeeDashboardPage`, `StudentPhotoBlock`).
4. **Service-helpers consolidation.** As noted above, a `getStudentPhotoUrl` helper had been added to `services/people.ts` ahead of P6 (probably by P7 prep work for `StudentThumbnail`). I kept the existing function/types byte-identical at the call surface and only appended the missing upload/delete + the `StudentPhotoMeta` type. No imports or other callers needed a change.
5. **Reuse of `StudentThumbnail`.** Considered using the existing `StudentThumbnail` component for the avatar visual, but the block's interactive states (broken-image fallback that resets on new uploads, custom 96px sizing with explicit border, status line keyed off the same query) are tighter to keep co-located. The two components share the React Query key (`['student-photo-url', studentId, 'thumb']`) so cache hits are still 1-to-1.
6. **`person.name` on the detail page.** The brief suggested checking for `extractPerson(s)?.name`. The existing page already extracts `const person = extractPerson(s)` on line 54 and uses `person.name` for the H1 — I reused `person.name` directly to keep parity with the rest of the page's data flow.
7. **Picker error placement.** When the picker rejects a file (size or MIME) the error replaces the action buttons until the user clicks "Try again". This means a user with no existing photo and a rejected file will only see the inline error + try-again link until the next file is selected — which feels right (the "Upload photo" CTA would otherwise present two affordances for the same action).
8. **`fileInputRef.current.value = ''` reset on selection.** Required so re-selecting the *same* file (after a rejected size/MIME or a cancelled modal) refires the `change` event. Without this, the second click would silently no-op, which would look like a broken UI.
